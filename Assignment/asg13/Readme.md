# 과제 13 : 병합 정렬과 퀵 정렬의 성능 비교

## 1. 구현 개요

| 항목        | 내용                                                                                                                                                |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 데이터      | 과제 12와 같은 데이터 : `rand() % 100000` 무작위 정수 (중복 허용), 고정 시드 `20261107`                                                             |
| 데이터 크기 | 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000                                                                                                     |
| 공정성      | 크기마다 원본 배열 1개를 만들고, 네 알고리즘 모두 `memcpy`로 복사한 배열을 정렬                                                                     |
| 정렬 확인   | ① `is_sorted()`로 오름차순인지 ② `qsort()`로 만든 정답과 `memcmp`로 비교해 원본과 같은 값들인지 확인 (실패 시 `[ERROR]` 출력) → 24개 결과 모두 정상 |
| 병합 정렬   | 하향식 재귀. 임시 배열 `tmp`(n칸)를 정렬 시작 시 한 번 할당해 모든 병합에서 재사용                                                                  |
| 퀵 정렬     | 과제 12와 같은 `partition()`, `median_of_three()` 사용. 피벗 선택(`select_pivot()`)만 First / Random / Median-3로 다름                              |

**과제 12와 같은 데이터인지 확인한 방법**

- 데이터 생성과 Random 피벗이 모두 `rand()`를 쓰므로, `rand()`를 호출하는 순서가 과제 12와 같아야 다음 크기의 데이터도 같아짐.
- 그래서 크기마다 첫 번째 정렬은 과제 12와 똑같이 `rand()`로 피벗을 뽑고, 실행시간 평균을 위한 추가 반복에서만 별도 난수(LCG)를 사용함.
- 확인 : 같은 환경(Linux)에서 GitHub에 제출한 과제 12 `QuickSort.c`와 First, Random의 비교 횟수가 6개 크기 모두 같았음 (예: n = 1,000에서 11,153 / 13,029). First의 비교 횟수는 데이터에 의해서만 정해지므로, 데이터가 같다는 근거가 됨.
- Median-3는 아래 "과제 12 코드에서 발견한 문제"를 고쳤기 때문에 과제 12와 비교 횟수가 조금 다름.

**과제 12 코드에서 발견한 문제 : Median-3에서 값이 사라짐**

- 과제 12의 `median_of_three()`는 구간에 원소가 2개뿐일 때 `mid == left`가 됨. 그러면 `a[left] = lo; a[mid] = md;`가 같은 칸에 두 번 쓰여서 값 하나가 사라짐 (예: `[5, 3]` → `[5, 5]`).
- 결과는 오름차순이라 `is_sorted()` 검사로는 잡히지 않았음. 과제 12 데이터로 확인해 보니 n = 20,000에서 1,397칸이 원본에 없는 값(중복된 값)으로 바뀌어 있었음.
- 과제 13에서는 `select_pivot()`에 `if (right - left < 2) break;`를 넣어 원소가 2개인 구간은 첫 원소를 피벗으로 쓰도록 고쳤음. 그리고 같은 문제를 다시 놓치지 않도록, 정렬 결과를 `qsort()` 정답과 비교하는 검사를 추가했음 (버그를 일부러 다시 넣으면 6개 크기 모두 `[ERROR]`가 출력되는 것을 확인함).

**비교 횟수 측정 규칙**

- 데이터 값끼리의 비교는 `less()`, `greater()`, `less_equal()` 함수로만 수행하고, 호출할 때마다 `cmp_count++`
- 병합 정렬 : `merge()`에서 `a[i] <= a[j]` 비교 (`<=`를 써서 같은 값의 순서를 유지하는 안정 정렬)
- 퀵 정렬 : partition의 `a[i] < pivot`, `a[j] > pivot` 비교 + Median-3의 중앙값 결정 비교(2~3회)
- `i <= mid`, `j <= right` 같은 인덱스 검사, 남은 원소 복사, swap, 난수 생성은 세지 않음

**실행시간 측정 방법**

- `clock_gettime(CLOCK_MONOTONIC)`으로 정렬 함수 호출 직전과 직후만 측정 (단위 ms)
- 데이터 생성, `memcpy` 복사, 출력은 측정 구간 밖에 있음
- 한 번의 정렬이 1 ms 안팎으로 짧아서, 같은 원본을 매번 새로 복사해 10회 정렬한 평균을 출력함
- 네 알고리즘 모두 같은 측정 함수 `measure()`를 사용함

## 3. 분석

### (1) 데이터 크기 증가에 따른 비교 횟수 변화

- n이 1,000 → 20,000으로 20배가 될 때 병합 정렬의 비교 횟수는 약 30배, 퀵 정렬은 약 26~32배 늘어남. 왜냐하면 두 알고리즘 모두 평균 비교 횟수가 O(n log n)이라서 n과 함께 log n도 커지기 때문임 (n·log₂n은 28.7배 증가).
- 병합 정렬은 모든 크기에서 비교 횟수가 가장 적음 (n = 20,000에서 Median3보다 약 20%, First보다 약 28% 적음). 30회 평균에서도 6개 크기 모두 병합 정렬이 가장 적었음 (Median3의 75~79%).
- 병합 정렬의 비율(비교 / n·log₂n)은 0.87 → 0.91로 거의 일정하고 1보다 작음. 왜냐하면 병합 정렬은 항상 정확히 반으로 나누어 깊이가 log₂n으로 고정되고, 한 번 병합할 때 비교는 최대 (두 구간 길이 합 − 1)번이며 한쪽 구간이 먼저 끝나면 남은 원소는 비교 없이 복사되기 때문임. 이론값 n·log₂n − 1.25n ≈ 260,754 (n = 20,000)와 측정값 260,937, 30회 평균 260,927이 거의 같음.
- 퀵 정렬의 비율은 1.12~1.37로 더 크고 크기마다 흔들림. 왜냐하면 분할이 피벗 값에 따라 정확히 반이 되지 않아 재귀 깊이가 log₂n보다 깊어지고(n = 20,000에서 24~33단계, 병합은 16단계), 한 번 분할할 때 구간 전체(약 n번)를 피벗과 비교하기 때문임.
- 보충 실험에서 병합 정렬은 정렬된 입력에서 오히려 비교가 줄었음 (148,016). 왜냐하면 왼쪽 구간 값이 모두 작아서 왼쪽이 먼저 끝나고, 오른쪽은 비교 없이 복사되기 때문임. 반대로 First 피벗은 약 2억 번(≈ n²/2)으로 O(n²)이 됨.

### (2) 두 정렬 알고리즘의 실행시간 차이

- 비교 횟수는 병합 정렬이 가장 적었지만, 실행시간은 모든 크기에서 병합 정렬이 가장 느렸음 (n = 20,000에서 Merge 3.05 ms, 퀵 정렬 2.24~2.40 ms). 2번 더 실행해도 Merge 2.91~3.59 ms, 퀵 정렬 2.09~2.61 ms로 병합 정렬이 가장 느렸음.
- 병합 정렬이 느린 이유는 **데이터 이동량**임. 왜냐하면 병합할 때마다 구간 전체를 `tmp`에 복사하고 다시 `a`로 되돌리므로, 각 단계마다 2n번씩 총 약 2n·log₂n번의 이동이 일어나기 때문임. 퀵 정렬은 제자리에서 자리가 틀린 원소만 swap함.
- 메모리 접근 범위도 다름. 퀵 정렬은 배열 하나만 읽고 쓰지만, 병합 정렬은 `a`와 `tmp` 두 배열을 오가므로 캐시에 올려야 할 데이터가 2배임.
- 즉 실행시간은 비교 횟수만이 아니라 "비교 + 데이터 이동 + 메모리 접근"의 합으로 정해진다는 것을 확인함.
- 퀵 정렬 세 방법끼리는 차이가 작고(n = 20,000에서 0.16 ms 이내), 다시 실행하면 순서가 바뀜. 왜냐하면 비교 횟수 차이가 10% 안팎이고, Random은 난수 생성, Median3는 중앙값 선택이라는 추가 비용이 각각 있어서 서로 상쇄되기 때문임. 1 ms 단위의 짧은 측정이라 실행할 때의 시스템 상태에도 영향을 받음.
- 단, 보충 실험(정렬된 입력)에서는 First가 492 ms로 병합 정렬(1.33 ms)보다 약 370배 느렸음. 병합 정렬은 입력과 상관없이 O(n log n)이 보장되지만, 퀵 정렬은 피벗이 나쁘면 O(n²)이 됨.

### (3) 두 정렬 알고리즘의 메모리 사용량 차이

- n = 20,000에서 병합 정렬은 81,376 Byte, 퀵 정렬은 2,000~2,720 Byte로 약 30~41배 차이가 남.
- 병합 정렬은 n에 비례해 늘어남 (n이 2배 → 메모리 약 2배). 왜냐하면 메모리의 대부분(98%)이 임시 배열 `tmp` = n × 4 Byte이기 때문임. 재귀 스택은 깊이가 log₂n이라 976 → 1,376 Byte로 조금만 늘어남.
- 퀵 정렬은 n이 20배가 되어도 1.4~1.7배만 늘어남. 왜냐하면 임시 배열 없이 제자리에서 정렬하고, 추가 메모리는 재귀 호출 스택(깊이 × 프레임 크기)뿐이며 깊이가 log n에 비례하기 때문임.
- 퀵 정렬 중에서는 Median3가 6개 크기 모두에서 가장 적음. 왜냐하면 분할이 가장 고르게 되어 재귀 깊이가 가장 얕기 때문임 (n = 20,000에서 Median3 24, First·Random 33).
- 보충 실험에서 First 피벗은 깊이가 20,000이 되어 스택만 1,600,080 Byte (≈ 20,000 × 80 Byte)를 사용함. 즉 퀵 정렬의 공간 복잡도는 평균 O(log n)이지만 최악에는 O(n)이고, 이때는 병합 정렬보다도 메모리를 더 많이 씀.

### (4) 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

- **비교 횟수** : 1회 측정에서는 크기마다 순위가 바뀜. Median3는 n = 16,000, 20,000에서 가장 적었지만, n = 1,000~8,000에서는 First보다 많았음. 왜냐하면 무작위 데이터에서는 첫 번째 원소도 사실상 무작위 원소라서, 한 번의 결과는 데이터 배치 운에 따라 흔들리기 때문임. 보충 실험 2에서 서로 다른 데이터 30개로 평균을 내면 Median3가 6개 크기 모두에서 가장 적었음 (First 대비 91~95%). 즉 한 번의 측정이 아니라 평균으로 보면 Median3가 분명히 효과적임.
- **안정성** : 비율(비교 / n·log₂n)의 흔들림 폭은 Median3가 1.14~1.24로 가장 좁고, First 1.12~1.29, Random 1.18~1.37임.
- **재귀 깊이와 메모리** : 비교 횟수와 달리 1회 측정에서도 Median3가 6개 크기 모두에서 가장 얕고 메모리도 가장 적음 (30회 평균 깊이도 n = 20,000에서 Median3 25.9, First 33.9). 왜냐하면 세 값의 중앙값은 최솟값·최댓값이 될 수 없어서 아주 치우친 분할이 생기지 않고, 재귀 깊이는 가장 치우친 분할 경로 하나로 정해지기 때문임.
- **실행시간** : 무작위 데이터에서는 세 방법의 차이가 작음 (n = 20,000에서 2.24~2.40 ms). 중앙값을 고르는 비교 2~3번과 swap이 추가되어, 분할이 고르게 된 효과가 일부 상쇄되기 때문임.
- **정렬된 입력** : First만 O(n²)으로 무너지고, Random과 Median3는 무작위 데이터와 비슷한 수준을 유지함. 따라서 입력 상태와 상관없이 안정적인 Median3가 가장 효과적임 (과제 12의 결론과 같음).

### (5) 시간 복잡도 및 공간 복잡도 차이

|             | 병합 정렬                          | 퀵 정렬                               |
| ----------- | ---------------------------------- | ------------------------------------- |
| 최선 시간   | O(n log n)                         | O(n log n)                            |
| 평균 시간   | O(n log n)                         | O(n log n)                            |
| 최악 시간   | **O(n log n)**                     | **O(n²)** (피벗이 계속 최솟값/최댓값) |
| 추가 공간   | **O(n)** 임시 배열 + O(log n) 스택 | 평균 **O(log n)**, 최악 O(n) 스택     |
| 제자리 정렬 | X                                  | O                                     |
| 안정 정렬   | O (`<=` 병합)                      | X (멀리 떨어진 원소끼리 swap)         |

- 병합 정렬은 분할 위치가 항상 가운데로 고정되어 있어서 입력과 상관없이 깊이가 log₂n이고, 시간이 O(n log n)으로 보장됨. 대신 병합 결과를 저장할 공간이 필요해 O(n) 메모리를 씀. → 실험에서 비교 횟수 비율 0.87~0.91 일정, 메모리는 n에 비례.
- 퀵 정렬은 분할 위치가 피벗 값에 따라 정해지므로 평균은 O(n log n)이지만 최악은 O(n²)임. 대신 제자리에서 정렬하므로 추가 공간이 재귀 스택뿐임. → 실험에서 메모리는 거의 일정, 정렬된 입력 + First에서 O(n²) 시간과 O(n) 스택이 실제로 나타남.
- 정리하면, 병합 정렬은 "메모리를 더 쓰는 대신 시간이 보장되는" 방식이고, 퀵 정렬은 "메모리를 거의 안 쓰고 평균적으로 빠르지만 피벗 선택이 중요한" 방식임.

### (6) 메모리 사용량의 측정 방법과 계산 기준

**측정 대상** : 정렬 함수가 실행되는 동안 필요한 최대 추가 메모리 = **힙 추가 할당 최대치 + 재귀 호출 스택 최대 사용량**

- 원본 배열 `origin`과 복사본 `work`는 네 알고리즘 공통 비용이므로 제외함.

**① 힙 메모리 (직접 계산)**

- 정렬 안에서의 동적 할당은 `track_malloc()` / `track_free()`로만 하며, 할당할 때 현재 사용량에 더하고 최대치(`heap_peak`)를 갱신함.
- 병합 정렬 : `tmp` 배열 `n × sizeof(int)` = n × 4 Byte (예: n = 20,000 → 80,000 Byte)
- 퀵 정렬 : 보조 자료구조를 쓰지 않으므로 0 Byte (Random도 난수 함수만 호출하고 따로 배열을 쓰지 않음)

**② 재귀 호출 스택 (주소 차이로 측정)**

- 정렬 함수 호출 직전에 `measure()`의 지역 변수 주소를 `stack_base`로 저장함.
- 재귀 함수(`merge_sort_rec`, `quick_sort_rec`)와 그 안에서 호출하는 `merge`, `partition`의 시작 부분에서 `STACK_PROBE()`로 지역 변수 주소를 확인하고, 가장 낮은 주소를 `stack_low`에 기록함.
- 스택은 높은 주소에서 낮은 주소로 자라므로, `stack_base − stack_low`가 정렬 중 사용한 최대 스택 크기임.
- 확인 : 이 실험 환경에서 재귀 1단계당 80 Byte가 늘어남. 병합 정렬 n = 20,000은 깊이 16 × 80 + 96 = 1,376 Byte, 정렬된 입력의 First는 20,000 × 80 + 80 = 1,600,080 Byte로, 측정값이 "깊이 × 80 Byte + 맨 위·맨 아래 프레임 일부"와 맞음.
- 한계 : 가장 깊은 함수 프레임 중 지역 변수 아래쪽 일부(수십 Byte)와 `less()` 같은 작은 함수의 프레임은 포함되지 않을 수 있음. 또 프레임 크기는 CPU·컴파일러·최적화 옵션에 따라 달라짐. 하지만 네 알고리즘 모두 같은 방식으로 재므로 비교에는 문제가 없음.

**③ 측정 시점**

- 비교 횟수와 메모리는 10회 반복 중 첫 번째 정렬에서 기록함. 실행시간은 10회 평균임.

## 4. 결론

- 비교 횟수 : 병합 정렬 < 퀵 정렬 (병합은 항상 반으로 나누고, 남은 원소는 비교 없이 복사하기 때문)
- 실행시간 : 무작위 데이터에서는 퀵 정렬이 더 빠름 (병합은 매 단계 2n번 복사가 필요하기 때문). 단 퀵 정렬은 나쁜 피벗에서 O(n²)으로 크게 느려짐
- 메모리 : 퀵 정렬이 훨씬 적음 (병합은 O(n) 임시 배열, 퀵은 O(log n) 스택)
- 피벗 선택 : Median-of-Three가 재귀 깊이·메모리가 가장 적고 정렬된 입력에서도 안정적임. 비교 횟수는 1회 측정에서는 순위가 바뀌지만, 30회 평균에서는 6개 크기 모두 가장 적었음

## 5. 실행 환경

- 위 결과 : Linux x86-64, gcc, 최적화 옵션 없음 (`gcc Sortcompare.c -o Sortcompare`)
- 보충 실험 2 : 같은 환경, `Sortcompare.c`의 정렬 함수를 그대로 불러 쓰는 별도 실험 코드
- `rand()` 구현과 함수 프레임 크기는 운영체제·CPU마다 달라서, macOS 등 다른 환경에서는 비교 횟수(퀵 정렬)와 메모리(스택 부분), 실행시간 숫자가 달라질 수 있음. 병합 정렬의 힙 메모리(n × 4 Byte)는 환경과 상관없이 같음
