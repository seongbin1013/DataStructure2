### 입력 형식 (괄호 표기법)

이전 과제와 동일한 방식이되, 이진트리는 왼쪽/오른쪽을 구분한다.

| 상황                | 표기     |
| ------------------- | -------- |
| 단말 노드           | `A`      |
| 왼쪽 자식만 있음    | `A(B)`   |
| 오른쪽 자식만 있음  | `A(,C)`  |
| 양쪽 자식 모두 있음 | `A(B,C)` |

각 자식 자리에는 같은 규칙이 재귀적으로 적용된다. 예: `A(B(D,E),C(,F))`

### 입력 검증

정상 트리 이외의 입력에 대해 다음을 오류로 거부한다(두 구현 동일).

| 입력 예                                     | 처리                                                                                                                                                                               |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `A(B,C))` , `A(B,C)TRAIL` , `A B`           | 트리 파싱이 끝난 뒤 공백이 아닌 문자가 남으면 오류                                                                                                                                 |
| `A(B,C,D)` (자식 3개)                       | 두 번째 자식 뒤에 `)`가 아닌 다른 문자가 오면 오류(`,` 뒤에 세 번째 값이 오면 그 자리에서 `)` 필요 오류로 걸림)                                                                    |
| `A(` , `A(,)` 등 불완전한 괄호              | `)` 를 찾지 못하면 오류                                                                                                                                                            |
| `)(` 처럼 루트 자리에 노드 이름이 없는 입력 | "유효한 루트 노드를 찾을 수 없습니다" 오류 (공백만 있는 입력은 빈 트리로 정상 허용)                                                                                                |
| 빈 입력 / 공백만 있는 입력                  | 오류가 아니라 노드 수 0개인 빈 트리로 허용(트리 정보·형태 판별 메뉴에서 "빈 트리입니다" 처리)                                                                                      |
| 32자 이상의 노드 이름                       | 잘라서 저장하지 않고 "이름이 너무 깁니다" 오류로 거부(서로 다른 긴 이름이 잘려서 같은 이름처럼 충돌하는 것을 방지)                                                                 |
| 매우 깊은(약 20단 이상) 편향 트리           | 배열 구현은 인덱스가 `2*i+1`씩 벌어지므로, 실용적 상한(칸 수 1,000,000)을 넘으면 계산이 오버플로되기 전에 오류로 거부. 연결 구현은 이 제약이 없다(4장·6장 참고)                    |
| 이름이 중복된 트리 (`A(B,B)`)               | 오류로 보지 않고 허용하되, 조회 시 전위 순회(현재 노드→왼쪽 전체→오른쪽 전체) 상 먼저 만나는 노드를 대상으로 함 — 두 구현이 항상 같은 노드를 고르도록 탐색 순서를 통일함(5장 참고) |

### 이진트리 출력 형식

이전 과제와 동일하게, 트리를 왼쪽으로 눕힌 형태로 출력한다. 전위 순회(preorder: 현재 노드 → 왼쪽 서브트리 → 오른쪽 서브트리) 순서로 출력하며, 깊이만큼 4칸씩 들여쓴 뒤 "+---"로 가지를 표시한다(루트만 예외로 접두어 없이 출력).

```
예: A(B(D,E),C(,F)) 입력 시

A
+---B
    +---D
    +---E
+---C
    +---F
```

두 구현(`ArrayBtree.c`, `LinkedBtree.c`) 모두 같은 입력에 대해 완전히 동일한 출력을 낸다(직접 비교 확인함).

## 1. 배열을 이용한 이진트리 구현 (`ArrayBtree.c`)

루트를 인덱스 0에 두고, 인덱스 `i` 노드에 대해

- 왼쪽 자식 인덱스 = `2*i + 1`
- 오른쪽 자식 인덱스 = `2*i + 2`
- 부모 인덱스 = `(i-1)/2`

로 계산하는 "완전이진트리 인덱싱" 방식을 사용했다. 트리가 편향될수록 실제로 쓰이지 않는 인덱스가 기하급수적으로 늘어난다는 점이 이 표현 방식의 핵심 특징이며, 3-[1]에서 이를 직접 측정한다.

배열 크기(용량)를 입력을 받기 전에는 알 수 없으므로, 입력 문자열을 **두 번** 파싱한다.

1. **1차 파싱**: 실제 필요한 최대 인덱스(`maxIndex`)만 계산 (저장은 하지 않음)
2. **2차 파싱**: `maxIndex + 1` 크기로 `calloc` 한 뒤 실제 데이터를 채움

이렇게 하면 필요한 만큼만 배열을 동적으로 할당하면서도, 과제에서 요구하는 "배열을 이용한 이진트리 표현(완전이진트리 인덱싱)" 방식 자체는 그대로 유지된다.

빈 칸 판정은 `name[0] == '\0'` (calloc으로 0 초기화되어 있음)으로 한다.

**정수 오버플로 방지**: `2*index+1`, `2*index+2`는 트리가 깊어질수록 값이 2배씩 커진다. 실제로 41단짜리 편향 트리를 넣어보면 `index`가 int 범위를 넘어 `signed integer overflow`(정의되지 않은 동작, UBSan으로 재현 확인)와 `calloc` 크기 폭주로 이어진다. 이를 막기 위해 재귀로 더 내려가기 전에 `index`가 실용적 상한(`MAX_CAPACITY = 1,000,000`, 약 2^20칸)을 넘는지 미리 검사하고, 넘으면 계산을 하기 전에 오류로 종료한다. 연결 구현은 인덱스 산술을 쓰지 않으므로 이 문제 자체가 없다(다만 매우 깊은 트리에서는 재귀 호출 스택 깊이 제한이라는 별개의, 두 구현이 공통으로 가진 제약이 있다).

### 트리 정보 / 형태 판별에서 배열 표현의 이점

- **완전 이진트리 판별**이 매우 간단해진다: 사용된 인덱스가 `0 ~ n-1` 범위를 빈틈없이 채우면(즉 `capacity == n`) 완전 이진트리이고, 중간에 빈 칸(gap)이 있으면 완전 이진트리가 아니다. 이는 완전 이진트리의 정의(마지막 레벨을 제외한 모든 레벨이 꽉 차고, 마지막 레벨은 왼쪽부터 채워짐)와 배열 인덱싱 방식이 정확히 대응하기 때문이다.
- **포화 이진트리 판별**: 노드 수 `n`이 `2^height - 1`과 같으면 포화이다 (높이 h인 이진트리가 가질 수 있는 최대 노드 수가 정확히 `2^h - 1`이고, 이는 모든 레벨이 꽉 찼을 때만 달성되므로).

## 2. 포인터를 이용한 연결 자료구조 구현 (`LinkedBtree.c`)

```c
typedef struct Node {
    char name[MAX_NAME];
    struct Node *left, *right;
} Node;
```

괄호 표기법을 재귀 하강 파싱하면서 노드가 등장하는 즉시 `malloc` 하여 왼쪽/오른쪽 포인터로 연결한다. 배열 구현과 달리 트리 크기를 미리 알 필요가 없으므로 **1차 파싱(크기 측정)이 필요 없다** — 이는 두 구현의 중요한 구조적 차이다.

- 완전 이진트리 판별: 레벨 순회(BFS)를 하면서 빈 자식(`NULL`)이 한 번이라도 나온 뒤에 실제 노드가 또 나오면 완전 이진트리가 아니다. 이 BFS용 큐는 동적 배열로 구현했는데, `malloc`/`realloc` 실패를 모두 점검하고, `realloc`은 반환값을 임시 포인터로 받은 뒤 성공한 경우에만 원래 포인터에 대입한다(실패 시 원본 포인터를 잃어버리는 흔한 실수를 피하기 위함).
- 포화 이진트리 판별: 재귀적으로 "리프이거나, 두 자식을 모두 가지면서 양쪽 서브트리의 높이가 같고 양쪽 다 포화"인지 확인한다.
- 편향 이진트리 판별: 모든 노드가 자식을 최대 1개만 가지면서(atMostOneChild), 그 자식이 전부 왼쪽으로만 있거나 전부 오른쪽으로만 있는지(방향 일관성)까지 확인한다. 자식이 최대 1개라는 조건만으로는 `A(B(,C))` 같은 지그재그(왼쪽-오른쪽 번갈아)도 편향으로 잘못 판정되기 때문이다. 이 정의 선택의 근거는 6장에 별도로 설명한다.

두 구현 모두 같은 정의를 사용하며, 실제 테스트에서 동일한 입력에 대해 항상 같은 결과를 냈다(아래 3. 참고).

## 3. 동작 확인 (컴파일 및 실행 검증)

`gcc -Wall -Wextra -std=c11`로 경고 없이 컴파일되며, AddressSanitizer/UBSan(`-fsanitize=address,undefined`)으로도 메모리 오류 없이 통과함을 확인했다.

다음 트리들로 두 구현의 출력이 항상 일치함을 확인했다.

| 입력               | 노드 수 | 검증 항목                                                                                       |
| ------------------ | ------- | ----------------------------------------------------------------------------------------------- |
| `A(B(D,E),C(,F))`  | 6       | 출력 모양, 트리정보(리프3/비리프3/높이3/차수2), 완전×/포화×/편향×, 자식·부모·형제 조회(D, C, A) |
| `A(B(D,E),C(F,G))` | 7       | 완전○/포화○/편향× (포화 이진트리)                                                               |
| `A(B(C(D)))`       | 4       | 완전×/포화×/편향○ (왼쪽 편향)                                                                   |
| `A(,B(,C(,D)))`    | 4       | 완전×/포화×/편향○ (오른쪽 편향)                                                                 |
| `A(B(D,E),C(F))`   | 6       | 완전○/포화×/편향× (완전이지만 포화는 아닌 경우)                                                 |
| `A`                | 1       | 완전○/포화○/편향○(자명), 리프1/비리프0/높이1/차수0                                              |
| `A(B(,C))`         | 3       | 편향× (지그재그는 편향으로 보지 않음)                                                           |
| `A(B,B)`           | 3       | 이름 `B` 조회 결과가 두 구현에서 완전히 동일(전위 순회 첫 매치인 왼쪽 B로 일치)                 |

```
[D] 자식 노드 : 없음
[D] 부모 노드 : B
[D] 형제 노드 : E
```

다음과 같은 잘못된/경계 입력도 두 구현에서 동일하게 오류로 처리됨을 확인했다(모두 실제 종료 코드 1로 종료, ASan/UBSan 크래시 없음).

| 입력                          | 결과                                                                                                                                                  |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `A(B,C))`                     | "트리 뒤에 불필요한 문자가 있습니다: )"                                                                                                               |

## 4. 3-[1] 메모리 사용량 비교

같은 노드 수(N=15)를 갖는 완전(포화)/일반/편향 이진트리 세 가지에 대해, `ArrayBtree.c`와 완전히 동일한 방식(1차 파싱으로 capacity 측정 → `calloc`으로 실제 할당 → 2차 파싱으로 채움)으로 배열을 실제로 만들고, `LinkedBtree.c`와 동일하게 노드마다 실제로 `malloc`하여 연결 트리도 실제로 만든 뒤, 두 자료구조가 요청한 바이트 수를 측정했다(`MemCompare.c`). capacity를 이론값으로 계산만 하지 않고 실제 `calloc` 호출까지 수행하도록 해서, 배열 쪽 측정도 연결 쪽과 같은 수준으로 "실측"이 되게 했다.

**측정 범위**: 두 값 모두 트리 노드 저장 공간만 포함한다. 입력 버퍼, 파싱 재귀 호출 스택, (연결 구현의 완전이진트리 판별에 쓰이는) BFS 순회 큐, malloc/calloc 내부 관리 오버헤드(청크 헤더 등, 힙 할당 1건당 보통 16바이트 내외)는 포함하지 않는다. 즉 "런타임에 실제로 요청한 할당 바이트 수" 비교이며, OS 수준 RSS 실측치가 아니다.

`./MemCompare` 실행 결과:

```
N = 15 로 노드 수를 통일한 세 가지 이진트리에 대한 실제 메모리 측정
sizeof(ArrayNode)  = 32 byte  (배열 한 칸: 이름 문자열)
sizeof(LinkedNode) = 48 byte  (이름 + 왼쪽포인터 + 오른쪽포인터)

트리 모양                N    높이  배열capacity  배열 메모리(B)  연결 메모리(B)  배열/연결
완전(포화) 이진트리      15     4          15            480             720      0.7x
일반 이진트리            15     6          63           2016             720      2.8x
편향 이진트리            15    15       16384         524288             720    728.2x
```

### 해석

- **완전(포화) 이진트리** (N=15=2⁴−1): 배열 표현에 필요한 capacity가 정확히 15로, 노드 수와 같다. 낭비되는 칸이 전혀 없고, 오히려 배열 구현(480B)이 연결 구현(720B)보다 메모리를 덜 쓴다 — 연결 구현은 노드마다 포인터 2개(16B)를 추가로 들고 있어야 하기 때문이다.
- **일반 이진트리**: 균형이 어긋난 만큼 배열 capacity가 63으로 늘어나(실제 사용 15/63 ≈ 24%), 배열 메모리가 연결 메모리의 약 2.8배가 된다.
- **편향 이진트리**: 모든 노드가 한쪽 자식만 가지므로 인덱스가 매 단계 약 2배씩(`2i+1`) 벌어진다. 15개 노드의 사슬은 배열 인덱스가 최대 16383까지 벌어져 capacity가 16384 — 실제 사용률이 15/16384 ≈ 0.09%에 불과하다. 배열 메모리는 연결 메모리의 약 **728배**에 달한다.
- 반대로 **연결 구현의 메모리 사용량은 트리 모양과 무관하게 항상 `N × sizeof(Node)`로 선형(720B 고정)** 이다. 트리가 어떤 모양이든 실제로 존재하는 노드 수만큼만 메모리를 쓰기 때문이다.

**결론**: 배열 기반 구현은 트리가 완전(또는 포화)에 가까울수록 유리하고, 편향에 가까울수록 메모리 낭비가 지수적으로 커진다. 연결 기반 구현은 노드당 오버헤드(포인터 2개, 이 구현에서는 16B)가 항상 붙지만 트리 모양에 영향을 받지 않는 선형 메모리를 보장한다. 따라서 트리 모양이 균형 잡힐 것이 보장되지 않는 일반적인 상황에서는 연결 구현이 메모리 측면에서 더 안전하다.

(참고: 여기서는 `sizeof`를 이용해 각 구현이 실제로 할당을 요청하는 바이트 수를 계산했다. malloc 자체의 내부 관리 오버헤드(청크 헤더 등, 보통 힙 할당 1건당 16B 내외)는 포함하지 않았는데, 연결 구현은 노드 수만큼 `malloc`을 여러 번 호출하므로 이 오버헤드까지 고려하면 연결 구현이 실제로는 표에 나온 값보다 조금 더 사용하지만, 편향 트리에서의 배열 구현 대비 격차(수백 배)를 뒤집을 정도는 아니다.)

## 5. 3-[2] 자식/부모/형제 노드 조회 프로그램과 효율성 비교

두 구현 모두 메뉴 `[4] 노드 관계 조회`에서 이름을 입력받아 자식·부모·형제 노드를 출력한다.

### 배열 구현 (`ArrayBtree.c`)

```c
static int findIdxPreorder(int idx, const char *name) {
    if (isEmptyIdx(idx)) return -1;
    if (strcmp(tree[idx], name) == 0) return idx;
    int found = findIdxPreorder(leftIdx(idx), name);
    if (found != -1) return found;
    return findIdxPreorder(rightIdx(idx), name);
}
...
int left  = 2*idx + 1;
int right = 2*idx + 2;
int parent = (idx - 1) / 2;
int sibling = (idx % 2 == 1) ? idx + 1 : idx - 1;
```

- 이름으로 노드 **위치(인덱스)를 찾는 과정**은, 배열 칸 전체(0..capacity-1)를 인덱스 순으로 훑는 게 아니라 실제 자식 링크(`leftIdx`/`rightIdx`)만 따라 내려가는 전위 순회로 구현했다. 존재하지 않는 칸은 애초에 방문하지 않으므로 최악의 경우에도 실제 노드 수 `n`만큼만 방문한다 — 즉 `O(n)`이다. (처음에는 `0..capacity-1`을 전부 훑는 방식으로 짰었는데, 이러면 편향 트리처럼 capacity가 n보다 훨씬 큰 경우 불필요하게 `O(capacity)`가 되어버린다. 이건 "배열 구현이라서 어쩔 수 없는" 한계가 아니라 순회 방식을 잘못 고른 것이었어서, 실제 링크만 따라가도록 고쳤다.)
- **인덱스를 이미 알고 있다면** 자식·부모·형제 모두 사칙연산 한 번으로 `O(1)`에 구해진다. 트리를 따라 실제로 이동(포인터를 따라가거나 자료구조를 다시 훑는 일)이 전혀 필요 없다.

### 연결 구현 (`LinkedBtree.c`)

```c
Node *findWithParent(Node *cur, Node *parent, const char *name, Node **outParent) {
    if (!cur) return NULL;
    if (strcmp(cur->name, name) == 0) { *outParent = parent; return cur; }
    Node *found = findWithParent(cur->left, cur, name, outParent);
    if (found) return found;
    return findWithParent(cur->right, cur, name, outParent);
}
```

- 이름으로 노드를 찾는 것은 트리를 전위 순회(DFS)해야 하므로 최악의 경우 `O(n)`이다. 위 배열 구현의 `findIdxPreorder`와 정확히 같은 순서(노드 자신 → 왼쪽 전체 → 오른쪽 전체)로 방문하므로, 이름이 중복된 트리(`A(B,B)`)에서도 두 구현이 항상 같은 노드를 찾는다(3장 표에서 확인).
- **자식**은 `target->left`, `target->right`로 `O(1)`에 바로 얻는다.
- 그러나 이 구현의 `Node`는 **부모 포인터를 저장하지 않는다.** 따라서 부모나 형제를 알아내려면, 탐색 시점에 부모를 같이 기록해 두는(위 코드처럼 `parent` 인자를 넘기는) 방법을 쓸 수밖에 없다. 만약 "이미 손에 쥔 `Node*` 포인터" 하나만 있고 이름 탐색 과정이 없었다면(예: 트리를 순회하다가 어떤 노드에 도달한 상태), 그 포인터만으로는 부모나 형제를 알아낼 방법이 전혀 없다 — 루트부터 다시 `O(n)` 탐색을 해야 한다.

### 결론: 어느 구현이 더 효율적인가

**현재 구현된 `[4] 노드 관계 조회` 메뉴 기준으로는, 두 구현의 비용이 사실상 같다.** 배열 구현은 `findIdxPreorder`로 이름을 찾으면 그 자리에서 나온 인덱스만으로 부모·형제까지 산술 연산으로 바로 구하고, 연결 구현의 `findWithParent`도 이름을 찾는 그 탐색 과정 중에 부모 노드를 이미 함께 확보해 둔다(재귀 인자로 `parent`를 넘기며 내려가기 때문). 즉 **"이름 검색은 O(n), 검색이 끝난 뒤 자식·부모·형제를 출력하는 것은 O(1)"** 이 두 구현 모두에 해당하며, 연결 구현이 부모를 얻기 위해 별도의 재탐색을 하지는 않는다. 이전 버전 설명에서 "인덱스/포인터를 이미 알 때 부모 접근이 배열은 O(1), 연결은 O(n)"이라고 쓴 것은 이 실제 조회 흐름을 정확히 반영하지 못한 표현이었다.

두 구현 사이에 실제로 비대칭이 남는 경우는 따로 있다: **이름 검색을 거치지 않고, 부모 정보 없이 노드의 위치(포인터 또는 인덱스)만 별도로 이미 들고 있는 상황**이다.

| 상황                                                                  | 배열 구현                                                           | 연결 구현                                                                                                   |
| --------------------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 이름 입력 → 관계(자식·부모·형제) 전체 출력 (현재 프로그램)            | O(n) 검색 + O(1) 관계 계산                                          | O(n) 검색(부모도 같이 확보) + O(1) 관계 계산                                                                |
| 자식 접근(위치를 이미 아는 상태)                                      | O(1)                                                                | O(1)                                                                                                        |
| **부모 접근** — 검색 과정 없이 위치(인덱스/포인터)만 따로 주어진 경우 | **O(1)** (`(i-1)/2` 산술 연산, 그 인덱스를 어디서 얻었든 항상 성립) | **O(n)** (`Node`에 부모 포인터가 없으므로, 그 포인터를 어디서 얻었든 부모를 알려면 루트부터 다시 훑어야 함) |

즉 **"배열이 더 효율적이다"는 주장은 지금 프로그램이 하는 일(이름으로 조회) 자체에 대한 이야기가 아니라, 부모 계보를 별도로 추적하지 않은 채 순수한 위치 정보만 주어졌을 때 그 위치로부터 부모를 되짚어낼 수 있느냐에 대한 구조적 차이**이다. 배열의 인덱스는 그 자체로 트리 상의 위치(와 부모·형제 관계)를 인코딩하고 있어서 산술 연산만으로 어느 방향이든 O(1)에 이동할 수 있지만, 연결 구현의 포인터는 "자신과 자식"만 알 뿐 "자신이 어디서 왔는지"는 담고 있지 않으므로, 부모 포인터 필드를 따로 두지 않는 한 그 정보를 다시 계산하려면 트리를 훑어야 한다.

다만 이 이점은 공짜가 아니다. 4장에서 보였듯 배열 구현은 트리가 편향될수록 그 "인덱스 산술"을 가능하게 하는 대가로 메모리를 지수적으로 더 쓴다. 연결 구현에 부모 포인터 필드(`struct Node *parent`)를 추가하면 부모·형제 조회도 `O(1)`로 만들 수 있지만, 그 대신 노드당 8바이트가 더 필요하다 — 이는 트리 모양과 무관하게 항상 붙는 고정 비용이라 편향 트리에서도 배열 구현처럼 폭발적으로 커지지는 않는다. 즉, **적은 대가로 O(1) 부모 접근이 필요하다면 연결 구현 + 부모 포인터 추가가 더 실용적인 절충안**이 되며, 이는 본 과제의 기본 구현(부모 포인터 없음)을 확장한 개선 방향으로 제안할 수 있다.

## 6. 정의에 따라 결과가 달라질 수 있는 사항

아래는 코드 버그가 아니라, 과제 설명이나 수업에서 명시적인 정의를 주지 않아 **선택이 필요했던** 부분이다. 확정 오류로 단정하지 않고, 현재 선택과 근거를 여기 문서화한다. 수업/교재가 다른 정의를 쓴다면 결과가 달라질 수 있다.

- **출력에서 왼쪽/오른쪽 자식 구분이 보이지 않음**: 트리 출력은 이전 과제와 동일하게 전위 순회 + "+---" 들여쓰기 형식을 그대로 따랐다(과제 지시사항의 "이전 과제와 동일하게" 요구를 우선함). 이 형식은 자식이 왼쪽인지 오른쪽인지를 시각적으로 구분하지 않으므로, `A(B)`와 `A(,B)`는 출력 모양이 같다. 왼쪽/오른쪽 구분은 출력이 아니라 `[4] 노드 관계 조회`에서 "B(왼쪽)" / "B(오른쪽)"으로 명시적으로 확인할 수 있다. 만약 출력 자체에서도 좌우를 구분해야 한다는 명확한 지시가 있다면(예: 왼쪽은 그대로, 오른쪽은 다른 기호로 표시) 형식을 바꿔야 하며, 그 경우 이전 과제 형식과는 달라진다.
- **트리의 높이 기준**: 루트 하나만 있을 때 높이를 1로 정의했다(레벨 수 기준). 높이를 0부터 세는 정의(루트만 있으면 높이 0)를 쓰는 교재도 있다. 어느 쪽이든 두 구현과 REPORT 전체에서 일관되게 "레벨 수, 루트=1" 기준을 썼다.
- **편향 이진트리의 정의**: "자식이 최대 1개인 사슬"이라는 느슨한 정의 대신, "모든 노드가 전부 왼쪽으로만 또는 전부 오른쪽으로만 자식을 가짐"이라는 좌편향/우편향 표준 정의로 구현했다(1장·2장 참고). 두 구현 모두 이 정의로 일치하게 고쳤다. 다만 수업에서 "자식이 최대 1개면 지그재그(`A(B(,C))`)도 편향으로 본다"는 느슨한 정의를 쓴다면 결과가 달라진다 — 그 경우 되돌리는 방법: `LinkedBtree.c`는 `isSkewed()`가 `atMostOneChild(n)`이라는 별도 함수를 이미 갖고 있으므로, `isSkewed()` 본문을 방향 검사(`checkChainDirection`) 없이 `return atMostOneChild(n);` 한 줄로 바꾸면 된다. `ArrayBtree.c`는 방향 추적 루프 하나로 합쳐 놨으므로, `printShapeInfo()`의 `allLeftChain`/`allRightChain` 계산 루프를 "자식이 2개인 노드가 하나라도 있으면 편향 아님"만 보는 원래 방식(`if (hasL && hasR) isSkewed = 0;`)으로 되돌려야 한다.

### 이번에 확정 오류로 보고 수정한 사항 (참고: ChatGPT 검토 의견 기준 분류)

- 트리 파싱 후 남는 문자를 검증하지 않던 것(`A(B,C))` 등이 통과되던 문제)
- 노드 이름이 31자를 넘으면 조용히 잘려 서로 다른 이름이 같아질 수 있던 문제
- 깊은 편향 트리에서 `2*index+1` 등이 정수 오버플로를 일으키던 문제(41단 트리로 직접 재현·수정 확인)
- `LinkedBtree.c`의 `isComplete()`에서 `malloc`/`realloc` 실패를 점검하지 않고, `realloc` 결과를 원본 포인터에 바로 대입하던 문제
- 배열 구현의 이름 검색이 전체 칸(`capacity`)을 훑어 불필요하게 느렸던 문제 → 실제 링크만 따라가는 전위 순회로 교체(O(n)으로 개선, 연결 구현과 탐색 순서도 통일)
- `MemCompare.c`가 배열 쪽은 실제 할당 없이 크기 계산만 하던 것 → `ArrayBtree.c`와 동일하게 실제 `calloc` 후 측정하도록 수정

### 선택적 개선(하지 않았거나 일부만 반영한 것)

- 이름이 중복된 트리에 대한 정책은 "오류로 거부"가 아니라 "허용하되 전위 순회 우선순위로 통일"을 선택했다. 과제에서 노드 이름이 서로 다르다고 가정한다면 애초에 발생하지 않는 상황이다.
- 연결 구현에 부모 포인터를 추가해 부모·형제 조회도 O(1)로 만드는 개선은 적용하지 않았다(5장에서 방향만 제안). 원한다면 추가로 구현할 수 있다.
- 매우 깊은 트리(수천~수만 단)에서의 재귀 호출 스택 한계는 두 구현 모두에 공통으로 남아있는 제약이며, 별도로 손대지 않았다(반복문 기반 재작성이 필요한 수준의 변경이라 이번 과제 범위를 벗어난다고 판단함).
