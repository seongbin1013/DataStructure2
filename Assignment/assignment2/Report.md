# 과제-02 : 이진트리 프로그램 구현 - 설명 문서

## 0. 파일 구성

| 파일            | 설명                                  |
| --------------- | ------------------------------------- |
| `ArrayBtree.c`  | 1. 배열을 이용한 이진트리 구현        |
| `LinkedBtree.c` | 2. 포인터를 이용한 연결 자료구조 구현 |
| `MemCompare.c`  | 3-[1] 메모리 사용량 비교 프로그램     |
| `Report.md`     | 본 설명 문서                          |

컴파일:

```
gcc -o ArrayBtree ArrayBtree.c
gcc -o LinkedBtree LinkedBtree.c
gcc -o MemCompare MemCompare.c
```

### 입력 형식 (괄호 표기법)

`A` (단말), `A(B)` (왼쪽만), `A(,C)` (오른쪽만), `A(B,C)` (양쪽). 예: `A(B(D,E),C(,F))`

잘못된 괄호, 파싱 후 남는 문자, 32자 넘는 이름, 20단 이상 깊은 편향 트리(오버플로 방지용 상한 초과)는 오류로 거부한다. 빈 입력은 오류가 아니라 빈 트리로 처리한다. 이름이 중복돼도 오류로 안 보고, 조회 시 전위 순회상 먼저 만나는 노드를 기준으로 한다.

### 출력 형식

이전 과제와 동일하게 전위 순회(현재 노드 → 왼쪽 → 오른쪽) 순서로, 깊이만큼 4칸 들여쓰고 `+---`로 표시한다.

```
A
+---B
    +---D
    +---E
+---C
    +---F
```

---

## 1. 배열 구현 (`ArrayBtree.c`)

루트를 인덱스 0에 두고 `왼쪽자식 = 2i+1`, `오른쪽자식 = 2i+2`, `부모 = (i-1)/2`로 계산하는 완전이진트리 인덱싱을 썼다.

크기를 미리 모르니 입력을 두 번 파싱한다: 1차로 필요한 최대 인덱스만 계산하고, 그 크기로 calloc한 뒤 2차 파싱으로 채운다.

편향 트리는 인덱스가 매 단계 두 배씩 벌어져서 깊어지면 `2*index+1` 계산이 int 범위를 넘는다(41단에서 실제 재현). 그래서 인덱스가 `MAX_CAPACITY(1,000,000)`를 넘으면 계산 전에 오류로 막는다.

완전 이진트리 판별은 `capacity == n`(빈 칸 없음)으로, 포화 판별은 `n == 2^height - 1`로 확인한다.

---

## 2. 연결 구현 (`LinkedBtree.c`)

```c
typedef struct Node {
    char name[MAX_NAME];
    struct Node *left, *right;
} Node;
```

노드가 나오는 즉시 malloc해서 연결하므로 1차 파싱이 필요 없다.

완전 이진트리는 BFS로 빈 자식 뒤에 노드가 또 나오는지 확인, 포화는 재귀로 양쪽 높이/포화 여부 확인, 편향은 자식이 최대 1개면서 방향(왼쪽만/오른쪽만)까지 일치하는지 확인한다. 자식 1개 조건만 보면 지그재그(`A(B(,C))`)도 편향으로 잘못 판정되기 때문에 방향 검사를 추가했다.

## 3. 동작 확인

`-Wall -Wextra -std=c11` 경고 없음, `-fsanitize=address,undefined` 통과 확인.

| 입력               | 노드 수 | 결과                             |
| ------------------ | ------- | -------------------------------- |
| `A(B(D,E),C(,F))`  | 6       | 완전×/포화×/편향×                |
| `A(B(D,E),C(F,G))` | 7       | 완전○/포화○/편향×                |
| `A(B(C(D)))`       | 4       | 편향○ (왼쪽)                     |
| `A(,B(,C(,D)))`    | 4       | 편향○ (오른쪽)                   |
| `A(B(D,E),C(F))`   | 6       | 완전○/포화×                      |
| `A`                | 1       | 완전○/포화○/편향○                |
| `A(B(,C))`         | 3       | 편향× (지그재그)                 |
| `A(B,B)`           | 3       | 이름 중복 조회 결과 두 구현 일치 |

두 구현 모두 위 케이스 전부 동일한 출력을 냈다. 잘못된 입력(닫는 괄호 초과, 트레일링 문자, 자식 3개, 루트 없음, 긴 이름, 41단 편향 트리)도 전부 exit code 1로 정상 거부됐고 ASan/UBSan 크래시는 없었다.

## 4. 메모리 사용량 비교 (`MemCompare.c`)

N=15로 통일한 완전/일반/편향 트리 세 가지를 실제로 calloc/malloc해서 측정했다.

```
트리 모양                N    높이  배열capacity  배열 메모리(B)  연결 메모리(B)  배열/연결
완전(포화) 이진트리      15     4          15            480             720      0.7x
일반 이진트리            15     6          63           2016             720      2.8x
편향 이진트리            15    15       16384         524288             720    728.2x
```

완전 이진트리는 배열 capacity가 노드 수와 같아서 배열이 더 적은 메모리를 쓴다. 편향 트리는 인덱스가 지수적으로 벌어져서 배열이 연결보다 728배 더 많은 메모리를 쓴다. 연결 구현은 트리 모양과 상관없이 항상 `N × sizeof(Node)`로 선형이다.

결론: 트리가 균형 잡힐 보장이 없다면 연결 구현이 메모리 면에서 더 안전하다.

## 5. 자식/부모/형제 조회 효율성 비교

배열은 실제 링크만 따라가는 전위 순회로 이름을 찾고(O(n)), 인덱스를 알면 부모/자식/형제를 산술 연산 한 번(O(1))으로 구한다. 연결도 전위 순회로 이름을 찾으면서(O(n)) 부모를 같이 확보하므로, 현재 프로그램(이름 → 관계 전체 출력) 기준으로는 두 구현의 비용이 사실상 같다.

차이가 나는 경우는 이름 검색 없이 위치(인덱스/포인터)만 따로 주어졌을 때다.

| 상황                                | 배열 | 연결 |
| ----------------------------------- | ---- | ---- |
| 자식 접근                           | O(1) | O(1) |
| 부모 접근 (검색 없이 위치만 주어짐) | O(1) | O(n) |

배열 인덱스는 산술 연산만으로 부모 위치를 알 수 있지만, 연결 구현의 `Node`는 부모 포인터가 없어서 되짚으려면 루트부터 다시 훑어야 한다. 연결 구현에 부모 포인터 필드를 추가하면 이것도 O(1)로 만들 수 있다(노드당 8바이트 추가, 트리 모양과 무관한 고정 비용).

## 6. 정의 관련 참고사항

- 출력은 좌우를 구분하지 않는 이전 과제 형식을 그대로 따랐다. 좌우 구분은 `[4] 노드 관계 조회`에서 확인 가능.
- 높이는 루트=1 기준으로 통일했다.
- 편향은 "자식 최대 1개"가 아니라 "전부 왼쪽만/전부 오른쪽만"으로 정의했다(지그재그 제외). 수업에서 느슨한 정의를 쓴다면, `LinkedBtree.c`는 `isSkewed()`를 `return atMostOneChild(n);`으로, `ArrayBtree.c`는 방향 검사 없이 `if (hasL && hasR) isSkewed = 0;`만 보도록 되돌리면 된다.
