# 과제 15 : 퀵 정렬과 AVL 트리 정렬의 성능 비교

## 1. 실행 방법

```bash
gcc QuickAVL.c -o QuickAVL
./QuickAVL

# 정렬 구간 / 삽입·삭제 구간을 나눈 상세 출력 (README 분석용)
gcc -DSHOW_DETAIL QuickAVL.c -o QuickAVL_detail
./QuickAVL_detail
```

- 4장의 결과는 최적화 옵션 없이(`gcc QuickAVL.c`) 컴파일해서 실행한 것임
- `-O2`를 붙이면 시간은 짧아지지만 비교 횟수·이동 횟수·최종 데이터 수는 똑같음 (5.1, 4.2 참고)

## 2. 구현 내용

### 2.1 데이터와 연산 생성

- 시드 `20261107`로 고정 (이전 과제와 같음), 값 범위 0 ~ 99,999, 중복 허용
- 데이터 크기마다 `원본 n개 → 연산 n/5개` 순서로 난수를 미리 생성함
  - `rand()`가 짝수이면 삽입, 홀수이면 삭제
  - 삽입·삭제할 값은 새 난수로 따로 생성
- 두 자료구조에 **같은 원본, 같은 연산 배열**을 그대로 적용함
- 난수 생성은 측정 구간 밖에서 끝내므로 시간·비교·이동 횟수에 들어가지 않음

### 2.2 [1] 퀵 정렬 + 정렬된 배열

- **피벗 선택 : Median-of-Three** (과제 13/14와 같은 알고리즘. 이번 과제에서는 데이터 이동 횟수를 세는 코드만 추가함)
  - `a[left], a[mid], a[right]`를 비교해 작은 값 / 중앙값 / 큰 값 순서로 다시 놓고, 중앙값을 맨 앞으로 옮긴 뒤 분할함
  - 원소가 2개인 구간은 가운데 원소가 없으므로 첫 원소를 피벗으로 씀
  - 고른 이유 : 이미 정렬된 배열에서도 O(n²)으로 무너지지 않고, Random과 달리 `rand()`를 쓰지 않아 데이터·연산 난수 순서를 바꾸지 않음
- 배열 크기 : `n + (삽입 연산 수)`만큼 한 번에 할당 (삽입이 모두 성공해도 넘치지 않는 최소 크기)
- **삽입** : 앞에서부터 `a[i] <= v`인 동안 선형 탐색 → `v`보다 큰 첫 위치를 찾고 뒤의 원소를 한 칸씩 뒤로 이동 후 대입
- **삭제** : 앞에서부터 `a[i] < v`인 동안 선형 탐색 → 멈춘 위치가 `v`와 같으면 뒤의 원소를 한 칸씩 앞으로 이동, 다르면 삭제하지 않음
  - 배열이 정렬되어 있으므로 `v` 이상인 값을 만나면 그 뒤에 `v`가 있을 수 없어 거기서 탐색을 멈춤 (여전히 선형 탐색)

### 2.3 [2] AVL 트리

```c
typedef struct AVLNode {
    int key;      /* 데이터 값 */
    int count;    /* 같은 값의 개수 (중복 저장) */
    int height;   /* 노드 높이 */
    struct AVLNode *left, *right;
} AVLNode;        /* 64비트 환경에서 32 Bytes */
```

- **정렬** : 원본 n개를 차례대로 AVL 트리에 삽입. 중위 순회 결과가 오름차순인지 확인함
- **중복 값** : 새 노드를 만들지 않고 `count`만 1 증가 / 삭제 시 `count > 1`이면 `count`만 1 감소 (한 개만 제거)
- **삭제(자식 2개)** : 오른쪽 부분 트리의 최소 노드(중위 후속자)를 떼어내고 그 값과 `count`를 현재 노드로 복사
- **균형 복구** : `rebalance()`에서 **높이 차이(균형 인수)만 보고** LL / LR / RR / RL 회전을 결정함
  - 새 값과 자식의 key를 비교해서 회전 종류를 정하는 방식은 데이터 값 비교가 추가로 생기므로 쓰지 않음

## 3. 측정 기준

| 항목          | 포함                                                                         | 제외                                                  |
| ------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------- |
| 총 수행시간   | 자료구조에 데이터 적재 + 정렬 + 모든 삽입·삭제 (10회 평균)                   | 난수 생성, 결과 확인(중위 순회 포함), 출력, 트리 해제 |
| 비교 횟수     | 정렬 중 값 비교, 삽입 위치 탐색, 삭제 대상 탐색에서의 **데이터 값 비교**     | 인덱스 범위 검사, NULL 검사, 균형 인수·높이 비교      |
| 데이터 이동   | 데이터 값의 복사·대입 (swap = 3회, 피벗 저장, 배열 원소 이동, 노드 key 대입) | 포인터 연결 변경(회전 포함), `count`·`height` 변경    |
| 메모리 사용량 | 자료구조(배열 또는 노드 전체)의 최대 크기 + 재귀 스택 최대 깊이              | 원본 배열(두 방법 공통 입력), 확인용 배열             |

- **같은 기준을 맞추기 위한 처리**
  - 적재 비용 : AVL은 노드를 만들 때 `key = v` 대입이 반드시 생기므로, 퀵 정렬도 원본을 배열로 옮기는 n회 대입을 이동 횟수와 시간에 넣음
  - AVL 비교 : 한 노드에서 `v < key`, `v > key`를 차례로 검사하므로 노드당 1~2회로 셈
  - `count`는 "그 값이 몇 개인지"를 나타내는 정보이고 데이터 값 자체가 아니므로 이동 횟수에서 뺌
- 메모리의 스택 부분은 재귀 함수 지역 변수의 주소 차이로 잼. 컴파일러·최적화 옵션에 따라 수백 Bytes 정도 달라질 수 있음
- `malloc` 내부에서 쓰는 관리 공간은 포함하지 않음 (할당기와 운영체제마다 방식이 달라서 코드에서 정확히 잴 수 없음)

## 5. 분석

### 5.1 총 수행시간과 비교 횟수의 차이

|      n | 총 시간 (Quick ÷ AVL) | 총 비교 (Quick ÷ AVL) |
| -----: | --------------------: | --------------------: |
|  1,000 |                1.65배 |                 7.1배 |
|  2,000 |                2.84배 |                12.4배 |
|  4,000 |                5.93배 |                22.0배 |
|  8,000 |                8.16배 |                39.3배 |
| 16,000 |               13.68배 |                71.9배 |
| 20,000 |               18.21배 |                88.6배 |

- **모든 크기에서 AVL 트리가 더 빠르고 비교 횟수도 적음.** 차이는 n이 커질수록 벌어짐 (시간 1.65배 → 18.21배)
- **정렬 구간만 보면 오히려 퀵 정렬이 유리함**
  - 비교 횟수는 둘 다 약 n·log₂n 수준이고, AVL이 10~17% 더 많음 (Quick ≈ 1.13~1.22·n·log₂n, AVL ≈ 1.29~1.36·n·log₂n). 왜냐하면 AVL은 오른쪽으로 내려갈 때 한 노드에서 `<`, `>`를 두 번 비교하기 때문임
  - 보충 실험(4.2)에서도 정렬 구간 시간은 AVL이 1.6~3.9배 느림. 왜냐하면 AVL은 원소마다 `malloc`을 호출하고, 메모리 여기저기에 흩어진 노드를 포인터로 따라가며, 돌아오면서 높이 갱신과 회전까지 하기 때문임. 퀵 정렬은 연속된 배열 하나를 앞뒤로 훑기만 함
- **전체 결과는 삽입·삭제 구간이 결정함**
  - 배열은 연산 1회마다 평균 "현재 크기의 절반" 정도를 선형 탐색함 (n = 20,000에서 연산당 약 10,446회 비교)
  - AVL은 높이가 17 이하로 유지되어 연산당 15.5~21.6회만 비교함
  - 그래서 퀵 정렬 쪽 총 비교 횟수의 90~99%가 삽입·삭제 구간에서 나옴. 정렬은 둘 다 O(n log n)으로 비슷하지만, 연산 비용이 배열 O(n), AVL O(log n)이라 차이가 남
- **최적화 옵션에 따라 작은 n에서 결과가 달라짐** (4.2 보충 실험)
  - 최적화 없음(Mac 실행 조건) : n = 1,000부터 AVL이 빠름
  - `-O2` : n = 1,000에서는 퀵 정렬이 빠르고(0.084 vs 0.123 ms), n = 2,000부터 AVL이 빠름
  - 이유 : 최적화가 없으면 `less()`, `swap()` 같은 함수가 비교·이동 1회마다 실제로 호출되므로, 비교·이동 횟수 차이가 시간에 거의 그대로 나타남. `-O2`에서는 이 함수들이 몇 개의 명령어로 줄어들어 배열의 연속 접근이 매우 빨라지고, 데이터가 작을 때는 AVL의 `malloc`·포인터 추적 비용이 더 크게 보임
  - 즉 "비교 횟수가 적다 = 항상 빠르다"는 아니며, 메모리 접근 방식(연속 vs 분산)과 실행 환경도 실제 시간에 영향을 줌. 다만 n이 커지면 두 조건 모두 AVL이 크게 앞섬

### 5.2 삽입·삭제 과정의 데이터 이동 횟수 차이

|      n | 이동 Quick | 이동 AVL | 성공한 삽입·삭제 1회당 이동 (Quick) |
| -----: | ---------: | -------: | ----------------------------------: |
|  1,000 |     61,727 |      114 |                                 537 |
|  4,000 |    848,038 |      383 |                               2,053 |
| 20,000 | 24,750,277 |    1,782 |                              10,291 |

- **배열** : 삽입·삭제 위치 뒤에 있는 모든 원소를 한 칸씩 옮겨야 함. 위치가 무작위이므로 평균 이동량은 현재 크기의 절반이고, n = 20,000에서 1회당 약 10,291회로 "크기 ÷ 2"와 거의 같음
- **AVL** : 이동이 생기는 경우는 두 가지뿐임
  - 새 값 삽입 시 새 노드에 `key` 대입 1회 (이미 있는 값이면 `count`만 바뀌므로 0회)
  - 자식이 2개인 노드 삭제 시 후속자의 `key` 복사 1회
  - 회전은 포인터 연결만 바꾸므로 데이터 이동이 전혀 없음
  - 그래서 이동 횟수가 연산 수보다도 적음 (n = 20,000 : 연산 4,000회, 이동 1,782회)
- **정렬 구간에서도 같은 구조 차이가 보임** : 퀵 정렬은 swap 1번에 이동 3회가 들어서 약 1.16~1.35·n·log₂n 이동(적재 n회 포함)이 생기지만, AVL은 노드 수만큼(≈ n)만 이동함. n = 20,000에서 332,603회 vs 18,082회
- **핵심 차이** : 배열은 "순서 = 메모리 위치"라서 순서를 지키려면 값을 직접 옮겨야 하고, AVL은 "순서 = 포인터 연결"이라서 연결만 바꾸면 됨

### 5.3 배열과 AVL 트리의 메모리 사용량 차이

- AVL이 **6.5~7.3배** 더 많은 메모리를 씀 (n = 20,000 : 89,788 vs 620,680 Bytes)
- **원소 1개당 크기** : 배열은 `int` 4 Bytes, AVL 노드는 `key + count + height + left + right` = 32 Bytes로 8배임
  - 실제 데이터(`key`)는 4 Bytes뿐이고 나머지 28 Bytes는 트리 구조를 유지하기 위한 정보임
- **8배가 아니라 약 7배인 이유**
  - 중복 값은 노드 하나에 `count`로 저장하므로 노드 수가 데이터 수보다 적음 (n = 20,000 : 최종 데이터 21,627개, 노드 최대 19,339개)
  - 배열은 삽입에 대비한 여유 공간(`n + 삽입 수`)을 미리 잡고, 재귀 스택도 따로 듦
- **보조 공간(스택)** : 퀵 정렬과 AVL 모두 재귀 깊이가 O(log n) 수준이라 1.2 ~ 1.9 KB로 작고, n이 20배가 돼도 1.4배 정도만 늘어남. 전체 메모리 차이는 거의 전부 노드 크기 차이에서 나옴
- 할당 횟수도 다름 : 배열은 큰 블록 1개만 할당하지만, AVL은 노드마다 `malloc`을 호출해 작은 블록을 수천~수만 개 만듦. 할당기 내부 관리 공간은 측정하지 않았으므로 표의 AVL 메모리는 "노드 자체 크기" 기준임

### 5.4 데이터 크기 증가에 따른 성능 변화

n이 20배(1,000 → 20,000) 늘 때 :

| 항목         |   Quick |    AVL | 이론                                   |
| ------------ | ------: | -----: | -------------------------------------- |
| 총 비교 횟수 | 370.9배 | 29.7배 | 배열 전체 O(n²) vs AVL 전체 O(n log n) |
| 총 이동 횟수 | 333.7배 | 17.9배 | 배열 O(n²) vs AVL O(n)                 |
| 총 시간      | 292.7배 | 26.5배 |                                        |
| 메모리       |  15.8배 | 16.8배 | 둘 다 O(n)                             |

- 연산 횟수도 n에 비례(0.2n)하므로, 배열은 "연산 수 O(n) × 연산당 비용 O(n)" = **O(n²)**로 커짐. 비교·이동 횟수가 330~370배로 n²의 증가율(400배)에 가까움
- AVL은 "연산 수 O(n) × 연산당 비용 O(log n)" = **O(n log n)**이라 비교 횟수가 약 30배만 늘어남
- 트리 높이는 12 → 17로 5만 늘었고, 항상 AVL 높이 상한(약 1.44·log₂(노드 수)) 안에 있음. 회전으로 균형을 계속 복구하기 때문에 연산당 비교 횟수가 15.5 → 21.6회로 천천히 늘어남
- 메모리는 둘 다 n에 비례해서 늘고, 두 방법의 비율(약 7배)은 크기가 달라져도 거의 일정함
- 따라서 n이 클수록 시간 격차가 벌어지고(1.65배 → 18.21배), n이나 연산 수가 더 커지면 차이는 계속 커질 것으로 예상됨

### 5.5 삽입·삭제가 반복되는 환경에서 유리한 자료구조

**AVL 트리가 유리함.** 왜냐하면 :

1. **탐색** : 배열은 이번 과제처럼 선형 탐색하면 O(n)임. AVL은 높이가 O(log n)으로 보장되어 탐색도 O(log n)임
2. **이동** : 배열은 이진 탐색으로 위치를 빨리 찾더라도 평균 n/2개를 옮겨야 하므로 삽입·삭제가 여전히 O(n)임. AVL은 포인터 연결만 바꾸므로 데이터 이동이 O(1)임
3. **균형 유지** : 일반 이진 탐색 트리는 입력 순서에 따라 한쪽으로 치우쳐 O(n)이 될 수 있지만, AVL은 회전으로 높이를 log 수준으로 유지하므로 최악의 경우에도 O(log n)임
4. **실험 결과** : n = 20,000의 삽입·삭제 구간만 보면 비교 약 485배, 이동 약 13,889배 차이가 나고, 보충 실험에서 시간도 22.7배(`-O2`) ~ 94.2배(최적화 없음) 차이가 남

단, 다음 경우에는 배열이 나을 수 있음 :

- **한 번 정렬하고 주로 읽기만 하는 경우** : 정렬 구간은 퀵 정렬이 더 빠르고(보충 실험 기준 1.6~3.9배), 배열은 인덱스로 바로 접근하거나 이진 탐색을 쓸 수 있음
- **데이터가 매우 작거나 메모리가 부족한 경우** : `-O2`에서 n = 1,000은 배열이 더 빨랐고, 메모리는 항상 AVL의 약 1/7 수준임

## 6. 결론

- 정렬만 하면 퀵 정렬이 유리함 : 비교 횟수는 비슷하지만 배열의 연속 접근이 AVL의 노드 할당·포인터 추적보다 빠름
- 정렬 후 삽입·삭제가 반복되면 AVL이 유리함 : 배열은 연산마다 O(n) 탐색 + O(n) 이동이 생기고, AVL은 O(log n) 탐색 + 포인터 변경뿐임. Mac 실행 결과 모든 크기에서 AVL이 빨랐음 (1.65배 → 18.21배)
- 데이터 이동은 구조 차이가 가장 크게 드러나는 지표임 : 배열은 순서를 지키려고 값을 옮기고, AVL은 연결만 바꿈
- 그 대가로 AVL은 원소당 32 Bytes 노드를 써서 메모리를 약 7배 더 씀
- n이 커질수록 배열 쪽 비용은 n²으로 늘어나므로, 삽입·삭제가 반복되는 환경에서는 AVL 트리가 유리함
