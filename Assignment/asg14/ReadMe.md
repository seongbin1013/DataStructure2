# 과제 14 : 힙 정렬, 퀵 정렬 및 병합 정렬의 성능 비교

## 1. 구현 개요

| 퀵 정렬     | 과제 13과 같은 코드. 피벗 선택(`select_pivot()`)만 First / Random / Median-3로 다름                                                                 |

**힙 정렬의 동작 (`heap_sort()`)**

1. 최대 힙 구성 : 마지막 내부 노드(`n/2 − 1`)부터 루트(0)까지 차례로 `sift_down()` 호출
2. 루트(최댓값) `a[0]`을 힙의 마지막 원소 `a[i]`와 교환
3. 힙 크기를 1 줄이고(`i`), 루트에서 `sift_down()`으로 힙 속성 복구
4. 힙 크기가 1이 될 때까지 2~3을 반복

- 배열에서 `i`의 왼쪽 자식은 `2i + 1`, 오른쪽 자식은 `2i + 2`임.
- `sift_down()`은 한 단계 내려갈 때마다 값 비교를 최대 2번 함 : (왼쪽 자식 vs 오른쪽 자식), (큰 자식 vs 부모).

**이전 과제와 같은 데이터인지 확인한 방법**

- 힙 정렬은 `rand()`를 쓰지 않으므로, 힙 정렬을 추가해도 `rand()` 호출 순서가 바뀌지 않음.
- 확인 : 같은 환경에서 과제 13 코드와 병합 정렬·퀵 정렬의 비교 횟수와 메모리 24개 값이 모두 같았음.

**비교 횟수 측정 규칙**

- 데이터 값끼리의 비교는 `less()`, `greater()`, `less_equal()` 함수로만 수행하고, 호출할 때마다 `cmp_count++`
- 힙 정렬 : 힙 구성과 힙 속성 복구에서 `sift_down()`이 하는 값 비교 모두
- 병합 정렬 : `merge()`의 `a[i] <= a[j]` 비교
- 퀵 정렬 : partition의 `a[i] < pivot`, `a[j] > pivot` 비교 + Median-3의 중앙값 결정 비교(2~3회)
- `child < size`, `i <= mid` 같은 인덱스 검사, swap, 복사, 난수 생성은 세지 않음

**실행시간 측정 방법**

- `clock_gettime(CLOCK_MONOTONIC)`으로 정렬 함수 호출 직전과 직후만 측정 (단위 ms)
- 데이터 생성, `memcpy` 복사, 출력은 측정 구간 밖에 있음
- 같은 원본을 매번 새로 복사해 10회 정렬한 평균을 출력함. 다섯 알고리즘 모두 같은 함수 `measure()`를 사용함
- Quick (Random)만 예외적으로, 1회차는 `rand()`로 피벗을 뽑고 2~10회차는 별도 난수(LCG)를 씀. 왜냐하면 `rand()`를 추가로 호출하면 다음 크기의 데이터가 이전 과제와 달라지기 때문임. 그래서 Random의 비교 횟수는 1회차 값이고, 실행시간은 피벗 순서가 조금씩 다른 10회의 평균임

## 3. 분석

### (1) 데이터 크기 증가에 따른 세 정렬 알고리즘의 비교 횟수 변화

- n이 1,000 → 20,000으로 20배가 될 때 비교 횟수는 힙 정렬 30.2배, 병합 정렬 30.0배, 퀵 정렬 26~32배 늘어남. 왜냐하면 세 알고리즘 모두 비교 횟수가 O(n log n)이라서 n과 함께 log n도 커지기 때문임 (n·log₂n은 28.7배 증가).
- 비교 횟수 순서는 6개 크기 모두 **병합 < 퀵 < 힙**이었음. n = 20,000에서 힙 정렬은 병합 정렬의 1.96배, 퀵 정렬의 1.42~1.56배임.
- **힙 정렬이 가장 많은 이유** : 루트의 최댓값을 꺼낼 때 힙의 맨 마지막 원소(작은 값)를 루트로 올리므로, 이 값은 거의 맨 아래 단계까지 다시 내려감. 내려가는 단계마다 "두 자식끼리 비교 + 큰 자식과 부모 비교"로 2번씩 비교하므로 한 번 꺼낼 때 약 2·log₂n번, 전체로 약 2n·log₂n번에 가까워짐. 실제 비율은 1.70 → 1.79로 2보다 조금 작은데, 힙이 줄어들수록 높이가 낮아지기 때문임.
- **힙 구성은 비교가 적음** : 힙 구성 단계는 약 1.88n번(n = 20,000에서 37,594번)으로 전체의 7%뿐이고 n에 비례함 (`gcc -DSHOW_DETAIL`로 따로 출력함). 왜냐하면 노드의 절반은 잎이라 내려갈 곳이 없고, 높이가 높은 노드는 수가 적기 때문임 (O(n)). 즉 비교의 93%는 정렬 단계(꺼내고 복구하기)에서 발생함.
- **병합 정렬이 가장 적은 이유** : 항상 정확히 반으로 나누어 깊이가 log₂n으로 고정되고, 병합할 때 원소 하나를 내보낼 때마다 비교는 1번이며, 한쪽 구간이 먼저 끝나면 남은 원소는 비교 없이 복사하기 때문임. 비율이 0.87~0.91로 거의 일정함.
- **퀵 정렬이 중간인 이유** : 원소 하나당 피벗과 1번만 비교하지만, 분할이 정확히 반이 되지 않아 재귀 깊이가 log₂n보다 깊어짐 (n = 20,000에서 24~33단계). 비율이 1.12~1.37로 크기마다 흔들리는 것도 분할이 피벗 값(데이터 배치)에 따라 달라지기 때문임.
- **입력 순서의 영향 (보충 실험)** : 정렬된 입력에서 힙 정렬은 529,074번으로 무작위일 때(510,672번)와 3.6%밖에 차이 나지 않음. 병합 정렬은 148,016번으로 줄고, First 피벗 퀵 정렬은 약 2억 번(≈ n²/2)으로 늘어남. 즉 힙 정렬은 비교 횟수가 가장 많지만 입력에 가장 덜 좌우됨.

### (2) 힙 정렬, 병합 정렬, 퀵 정렬의 실행시간 차이

- 실행시간 순서는 6개 크기 모두 **퀵 < 병합 < 힙**이었음. n = 20,000에서 퀵 2.70~2.80 ms, 병합 3.98 ms, 힙 5.30 ms임. 9번 반복 실행해도 이 순서가 유지되었음 (n = 4,000에서 한 번만 병합과 힙이 뒤바뀜).
- 다만 실행시간은 비교 횟수·메모리와 달리 실행마다 10~30% 흔들림. 왜냐하면 한 번의 정렬이 0.1~5 ms로 짧아서 CPU 상태와 다른 프로그램의 영향을 받기 때문임. 그래서 10회 평균을 쓰고, 아래 분석은 반복 실행에서도 유지되는 차이만 근거로 삼았음.
- **힙 정렬이 가장 느린 이유**
  - 비교 횟수가 가장 많음 (퀵의 약 1.5배, 병합의 약 2배).
  - 꺼낼 때마다 루트에서 잎 근처까지 내려가며 swap하므로 데이터 이동도 많음.
  - 부모 `i`에서 자식 `2i + 1`로 건너뛰므로 배열의 멀리 떨어진 칸을 오가게 됨. 퀵·병합 정렬은 배열을 앞에서부터 차례로 읽으므로 캐시를 더 잘 활용함 (일반적으로 알려진 원인이며, 이 실험에서 캐시를 직접 측정하지는 않았음).
  - 비교마다 `less()` 함수를 호출하는 비용도 있음. 비교가 가장 많은 힙 정렬이 이 비용을 가장 많이 치름.
- **병합 정렬이 비교는 가장 적은데 퀵보다 느린 이유** : 병합할 때마다 구간 전체를 `tmp`에 복사하고 다시 `a`로 되돌리므로, 총 약 2n·log₂n번의 데이터 이동이 일어나기 때문임. 퀵 정렬은 제자리에서 자리가 틀린 원소만 swap함.
- **비교 횟수와 실행시간이 비례하지 않음** : 병합 정렬은 퀵보다 비교가 20~28% 적지만 시간은 약 1.46~1.48배였고(n = 20,000), 힙 정렬은 병합보다 비교가 1.96배 많지만 시간은 1.33배였음. 즉 실행시간은 "비교 + 데이터 이동 + 메모리 접근 방식"의 합으로 정해짐.
- **이 순서는 최적화 없이 측정한 결과임** : `gcc -O2`로 다시 빌드하면 n = 20,000에서 힙 1.88~1.94 ms, 병합 1.85~1.99 ms로 둘이 거의 같아짐. 왜냐하면 최적화로 `less()`, `swap()` 호출이 인라인되어 힙 정렬의 함수 호출 비용이 사라지는 반면, 병합 정렬의 `tmp` 복사는 메모리 대역폭 비용이라 최적화로 줄지 않기 때문임. 즉 "힙이 병합보다 느리다"는 이 빌드 조건에서의 결과임. 퀵 정렬이 가장 빠른 것은 `-O2`에서도 같았음.
- **정렬된 입력 (보충 실험)** : First 피벗 퀵 정렬은 540 ms로 힙 정렬(3.81 ms)보다 약 142배 느림. 힙 정렬과 병합 정렬은 입력과 상관없이 O(n log n)이 유지됨.

### (3) 세 정렬 알고리즘의 메모리 사용량 차이

- n = 20,000에서 힙 정렬 188 Byte, 퀵 정렬 2,000~2,720 Byte, 병합 정렬 81,376 Byte임. 힙 정렬을 1로 보면 퀵 정렬은 약 11~15배, 병합 정렬은 약 433배임 (병합 ÷ 퀵은 30~41배).
- **힙 정렬 : 188 Byte로 n과 상관없이 일정함.** 왜냐하면 입력 배열 자체를 힙으로 쓰고, `sift_down()`을 반복문으로 구현해 재귀가 없기 때문임. 필요한 것은 `run_sort()` → `heap_sort()` → `sift_down()`의 함수 프레임 1개씩(인덱스 변수 몇 개)뿐임.
- **퀵 정렬 : n이 20배가 되어도 1.4~1.7배만 늘어남.** 임시 배열은 없지만 재귀 호출 스택(깊이 × 80 Byte + 80)이 필요하고, 깊이가 log n에 비례하기 때문임. Median3가 6개 크기 모두에서 가장 적었음 (분할이 고르게 되어 재귀가 가장 얕음).
- **병합 정렬 : n에 비례해 늘어남 (n 2배 → 약 2배).** 메모리의 대부분이 임시 배열 `tmp` = n × 4 Byte이기 때문임 (n = 20,000에서 98%, n = 1,000에서는 80%). 재귀 스택은 976 → 1,376 Byte로 조금만 늘어남.
- 보충 실험에서 First 피벗 퀵 정렬은 깊이가 20,000이 되어 1,600,080 Byte를 사용함. 힙 정렬은 이때도 188 Byte로 같았음. 즉 힙 정렬만 n과 입력 순서 모두에 상관없이 추가 메모리가 일정함 (병합 정렬도 입력 순서에는 영향받지 않지만 n에 비례해 늘어남).

### (4) 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

- **비교 횟수** : Median3가 6개 크기 모두에서 가장 적었음. 왜냐하면 세 값의 중앙값은 한 값보다 전체 중앙값에 가까울 확률이 높아 분할이 더 고르게 되기 때문임. First와 Random은 서로 앞서는 쪽이 크기마다 바뀌고 차이도 작음. 왜냐하면 데이터가 무작위이면 첫 번째 원소도 사실상 무작위로 고른 원소와 같기 때문임.
- **재귀 깊이와 메모리** : Median3가 6개 크기 모두에서 가장 얕고 메모리도 가장 적음 (n = 20,000에서 깊이 24, First·Random 33). 왜냐하면 세 값의 중앙값은 최솟값·최댓값이 될 수 없어서 아주 치우친 분할이 생기지 않기 때문임.
- **실행시간** : 무작위 데이터에서는 세 방법의 차이가 작고(n = 20,000에서 0.10 ms 이내) 다시 실행하면 순서가 바뀜. Random은 난수 생성, Median3는 중앙값 선택이라는 추가 비용이 있어 분할이 좋아진 효과와 상쇄되기 때문임.
- **정렬된 입력** : First만 O(n²)으로 무너지고(약 2억 번, 540 ms), Random과 Median3는 무작위 데이터와 비슷한 수준을 유지함. 따라서 정렬된 입력에서도 안정적인 Median3가 가장 효과적임. 단 Median3도 세 표본이 계속 치우치도록 꾸민 입력에서는 이론상 O(n²)이 될 수 있음.
- 어떤 피벗 방법이든 무작위 데이터에서는 퀵 정렬이 힙·병합 정렬보다 빨랐음.

### (5) 세 정렬 알고리즘의 시간 복잡도 및 공간 복잡도 비교

|             | 힙 정렬        | 병합 정렬                          | 퀵 정렬                               |
| ----------- | -------------- | ---------------------------------- | ------------------------------------- |
| 최선 시간   | O(n log n)     | O(n log n)                         | O(n log n)                            |
| 평균 시간   | O(n log n)     | O(n log n)                         | O(n log n)                            |
| 최악 시간   | **O(n log n)** | **O(n log n)**                     | **O(n²)** (피벗이 계속 최솟값/최댓값) |
| 추가 공간   | **O(1)**       | **O(n)** 임시 배열 + O(log n) 스택 | 평균 **O(log n)**, 최악 O(n) 스택     |
| 제자리 정렬 | O              | X                                  | O                                     |
| 안정 정렬   | X              | O (`<=` 병합)                      | X                                     |

(힙 정렬의 최선 O(n log n)은 값이 서로 다른 경우 기준임. 힙 구성만 보면 O(n)임)

- **힙 정렬** : 힙의 높이가 항상 log₂n 이하라서 입력과 상관없이 O(n log n)이 보장되고, 배열 안에서 힙을 유지하므로 추가 공간이 O(1)임. → 실험에서 메모리 188 Byte 고정, 정렬된 입력에서도 비교 횟수가 3.6%만 변함. 대신 상수(비율 약 1.8)가 가장 커서 실제로는 가장 느렸음.
- **병합 정렬** : 분할 위치가 항상 가운데라서 O(n log n)이 보장되지만, 병합 결과를 담을 O(n) 공간이 필요함. → 실험에서 비율 0.87~0.91로 일정, 메모리는 n에 비례.
- **퀵 정렬** : 분할이 피벗에 따라 달라져 평균 O(n log n), 최악 O(n²)임. 제자리 정렬이라 추가 공간은 재귀 스택뿐임. → 실험에서 가장 빨랐지만, 정렬된 입력 + First에서 O(n²) 시간과 O(n) 스택이 실제로 나타남.
- 정리하면 세 알고리즘은 같은 O(n log n)이라도 강점이 다름 : 힙 정렬은 "메모리가 가장 적고 최악도 보장", 병합 정렬은 "비교가 가장 적고 최악도 보장(안정 정렬)", 퀵 정렬은 "평균적으로 가장 빠름".

### (6) 메모리 사용량의 측정 방법과 계산 기준

**측정 대상** : 정렬 함수가 실행되는 동안 필요한 최대 추가 메모리 = **힙(동적 할당) 최대치 + 호출 스택 최대 사용량**

- 원본 배열 `origin`과 복사본 `work`, 정답 확인용 `ref`는 공통 비용이므로 제외함.
- 아래에서 "힙 메모리"는 `malloc`으로 할당하는 영역을 뜻하며, 자료구조 힙(최대 힙)과는 다른 말임.

**① 힙 메모리 (직접 계산)**

- 정렬 안에서의 동적 할당은 `track_malloc()` / `track_free()`로만 하며, 할당할 때 현재 사용량에 더하고 최대치(`heap_peak`)를 갱신함.
- 힙 정렬 : 0 Byte (입력 배열 자체를 힙으로 사용)
- 병합 정렬 : `tmp` 배열 `n × sizeof(int)` = n × 4 Byte (예: n = 20,000 → 80,000 Byte)
- 퀵 정렬 : 0 Byte (보조 자료구조 없음)

**② 호출 스택과 보조 변수 (주소 차이로 측정)**

- 정렬 함수 호출 직전에 `measure()`의 지역 변수 주소를 `stack_base`로 저장함.
- `heap_sort`, `sift_down`, `merge_sort_rec`, `merge`, `quick_sort_rec`, `partition`의 시작 부분에서 `STACK_PROBE()`로 지역 변수 주소를 확인하고, 가장 낮은 주소를 `stack_low`에 기록함.
- 스택은 높은 주소에서 낮은 주소로 자라므로, `stack_base − stack_low`가 정렬 중 사용한 최대 스택 크기임. 함수의 지역 변수(보조 변수)도 스택에 있으므로 이 값에 포함됨.
- 확인 : 이 환경에서 재귀 1단계당 80 Byte가 늘어남. 병합 정렬 n = 20,000은 깊이 16 × 80 + 96 = 1,376 Byte, 정렬된 입력의 First는 20,000 × 80 + 80 = 1,600,080 Byte로 측정값과 맞음. 힙 정렬은 재귀가 없어 `run_sort` → `heap_sort` → `sift_down` 프레임만큼인 188 Byte로 고정됨.
- 측정 경계 : `less()`, `swap()`, `select_pivot()`처럼 재귀하지 않는 함수에는 프로브를 넣지 않았음. 왜냐하면 이 함수들의 프레임은 재귀 깊이에 비례하지 않는 상수 비용이어서, 빼는 편이 "깊이 × 80 Byte" 관계를 그대로 보여 주기 때문임. 프로브를 추가해 보면 알고리즘별로 56~148 Byte가 더 잡히지만, 세 알고리즘의 순서와 증가 추세는 바뀌지 않았음.
- 한계 1 : 프레임 크기는 CPU·컴파일러·최적화 옵션에 따라 달라짐. 최적화를 켜면 함수가 인라인되어 프레임이 아예 사라질 수 있음 (`clang -O2`에서는 힙 정렬이 0 Byte로 측정됨). 그래서 5장에 적은 대로 최적화 없이 측정했음.
- 한계 2 : 다섯 알고리즘 모두 같은 방식으로 재므로 알고리즘 사이의 비교에는 문제가 없음.

**③ 측정 시점**

- 비교 횟수와 메모리는 10회 반복 중 첫 번째 정렬에서 기록함. 실행시간은 10회 평균임.

## 4. 결론

- 비교 횟수 : 병합 < 퀵 < 힙 (힙 정렬은 꺼낼 때마다 한 단계에 2번씩 비교하며 바닥까지 내려가기 때문)
- 실행시간 : 퀵 < 병합 < 힙 (6개 크기 모두, 최적화 없이 측정). 병합은 복사량, 힙은 비교 횟수와 띄엄띄엄한 접근·함수 호출 비용 때문에 느림. 단 `-O2`로 빌드하면 힙과 병합이 거의 같아짐
- 메모리 : 힙(188 Byte, 일정) < 퀵(log n에 비례) < 병합(n에 비례)
- 피벗 선택 : Median-of-Three가 비교 횟수·재귀 깊이·메모리 모두 가장 적고 정렬된 입력에서도 안정적임
- 최악의 경우까지 보면 힙 정렬과 병합 정렬은 O(n log n)이 보장되지만 퀵 정렬은 O(n²)이 될 수 있고, 이번 실험(정렬된 입력)에서는 First 피벗에서 실제로 나타남

## 5. 실행 환경

- 위 결과 : Linux x86-64, gcc 13.3, 최적화 옵션 없음 (`gcc SortCompare.c -o SortCompare`). 메모리 값은 이 빌드 조건에서의 실측값이며, 최적화 옵션을 켜면 달라짐
- `rand()` 구현과 함수 프레임 크기는 운영체제·CPU마다 달라서, macOS 등 다른 환경에서는 비교 횟수와 메모리(스택 부분), 실행시간 숫자가 달라질 수 있음. 병합 정렬의 힙 메모리(n × 4 Byte)는 환경과 상관없이 같음
