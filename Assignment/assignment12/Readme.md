# 과제 12 : 퀵 정렬의 피벗 선택에 따른 성능 비교

## 1. 구현 개요

| 항목        | 내용                                                                        |
| ----------- | --------------------------------------------------------------------------- |
| 데이터      | `rand() % 100000` 무작위 정수 (중복 허용), 고정 시드 `20261107`             |
| 데이터 크기 | 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000                             |
| 공정성      | 크기마다 원본 배열 1개를 만들고, 세 방법 모두 `memcpy`로 복사한 배열을 정렬 |
| 정렬 확인   | 정렬 후 `is_sorted()`로 오름차순 여부 검사 (실패 시 `[ERROR]` 출력)         |

**피벗 선택만 다르고 분할은 같음**

```
select_pivot()  →  피벗을 a[left]로 swap  →  partition()  (세 방법 공통)
```

- First : `left`
- Random : `left + rand() % (right-left+1)` (분할할 때마다 새로 뽑음)
- Median-3 : `a[left], a[mid], a[right]`의 중앙값 (산술평균 아님)

**비교 횟수 측정 규칙**

- 데이터 값끼리의 비교는 `less()`, `greater()` 함수로만 수행하고, 호출할 때마다 `cmp_count++`
- partition의 `a[i] < pivot`, `a[j] > pivot` 비교와 Median-3의 중앙값 결정 비교(2~3회)를 셈
- `i <= right` 같은 인덱스 검사, 난수 생성, swap(데이터 이동)은 세지 않음

**메모리 할당 검사**

- `main()`의 배열 할당과 `quick_sort_iter()`의 스택 할당 모두 `malloc` 결과가 `NULL`인지 검사함

## 3. 분석

### (1) 데이터 크기 증가에 따른 비교 횟수 변화

- n이 1,000에서 20,000으로 20배 커질 때, 비교 횟수는 세 방법 모두 약 28배 늘어남 (First 27.6배, Random 28.4배, Median-3 28.3배). 왜냐하면 퀵 정렬의 평균 비교 횟수가 O(n log n)이라서, n이 늘면 log n 항도 함께 커지기 때문임. 실제로 n·log₂n도 같은 구간에서 28.7배 늘어나 측정값과 거의 일치함.
- 세 방법 모두 비교 횟수가 n·log₂n의 약 1.2~1.4배 범위에 있음. 즉 무작위 데이터에서는 세 방법 모두 평균적인 O(n log n) 동작을 보임.
- 이론값과도 맞음. 무작위 피벗의 평균 비교 횟수는 약 2n ln n ≈ 1.39 n log₂n, Median-3는 약 1.19 n log₂n으로 알려져 있음.

### (2) 피벗 선택 방법별 성능 차이

- **본 실험** : Median-3가 6개 크기 모두에서 비교 횟수가 가장 적었음. First 대비 86.4% ~ 100.0% 수준이고, n = 8,000에서 차이가 가장 컸음 (약 1만 9천 번 적음). n = 4,000에서는 First와 18번 차이로 거의 같았음.
- **First vs Random** : 크기마다 앞서는 쪽이 바뀌고 차이도 작음 (최대 약 3.5%). 왜냐하면 데이터 자체가 무작위이면 "첫 번째 원소"도 사실상 무작위로 고른 원소와 같기 때문임.
- **안정성** : 비교 횟수 / n·log₂n 값이 Median-3는 1.19~1.21로 거의 일정했지만, First와 Random은 1.19~1.39로 크기에 따라 크게 흔들림. 즉 Median-3는 평균만 낮은 게 아니라 결과가 데이터 배치에 덜 좌우됨. 보충 실험 1의 범위도 Median-3가 가장 좁았음 (n = 20,000에서 Median-3 약 2.6만, First 약 5.3만).
- **정렬된 / 역순 데이터** : First는 약 2억 번으로 무작위일 때보다 약 550배 늘어남 (O(n²)). Random과 Median-3는 무작위 데이터와 비슷한 수준을 유지함.

### (3) 피벗 선택이 분할 결과와 비교 횟수에 영향을 주는 이유

- 한 번 분할할 때의 비교 횟수는 구간 길이 n에 비례(약 n번)하므로, 전체 비교 횟수는 **재귀 트리의 깊이**에 따라 정해짐.
- 피벗이 중앙값에 가까우면 구간이 반씩 나뉘어 깊이가 log₂n이 되고, 전체 비교는 약 n log₂n임.
- 피벗이 최솟값이나 최댓값이면 한쪽은 0개, 다른 쪽은 n−1개가 되어 깊이가 n이 되고, 전체 비교는 n + (n−1) + … ≈ n²/2임. 보충 실험 2에서 First의 200,029,998 ≈ 20,000² / 2가 정확히 이 경우임.
- **First** : 입력 순서에 그대로 의존함. 왜냐하면 정렬된 데이터에서는 첫 원소가 항상 최솟값이기 때문임.
- **Random** : 입력 순서와 상관없이 매번 무작위로 고르므로 최악의 경우가 계속 나올 확률이 매우 낮음. 다만 한 번 고른 피벗이 치우칠 수는 있어 편차는 First와 비슷함.
- **Median-3** : 세 값 중 가운데 값은 최솟값·최댓값이 될 수 없어서 극단적인 분할이 생기지 않음. 또 세 값의 중앙값은 한 값보다 전체 중앙값에 더 가까울 확률이 높아서 분할이 더 고르게 됨. 중앙값을 고르는 데 비교가 2~3번 더 들지만, 깊이가 줄어 아끼는 비교가 훨씬 많음.

### (4) 어떤 방법이 효과적이었는지

- **Median-of-Three가 가장 효과적이었음**. 왜냐하면 본 실험의 모든 크기에서 비교 횟수가 가장 적었고, 30회 평균에서도 가장 적었고, 결과의 흔들림이 가장 작았고, 정렬·역순 입력에서도 성능이 유지되었기 때문임.
- Random도 최악의 경우를 피한다는 점에서 효과적이지만, 무작위 데이터에서는 First와 평균이 거의 같음.
- First는 무작위 데이터에서는 문제가 없지만 입력이 정렬되어 있으면 O(n²)이 되므로 실제로 쓰기에는 위험함.
- 단, n = 4,000처럼 1회 측정에서는 차이가 거의 없는 경우도 있으므로, 피벗 방법을 비교할 때는 여러 데이터에 대한 평균으로 판단해야 함.

### 구현 중 발견한 문제 : Median-3 + 역순 데이터

처음에는 중앙값의 위치만 찾아 `a[left]`와 swap했는데, 역순 데이터에서 Median-3가 약 5천만 번(O(n²))으로 나빠짐. 정확한 원인은 swap으로 구간 맨 앞 값과 가운데 값이 서로 바뀐 상태에서 분할하면 다음 하위 구간의 first/middle/last 배치가 다시 한쪽으로 치우치게 되는 것으로 보임 (실험으로 확인한 것은 O(n²)이 된다는 결과까지임). 그래서 세 값을 비교한 뒤 `a[left] ≤ a[mid] ≤ a[right]`로 정리해 두도록 고쳤고, 그 후 역순 데이터도 294,482번으로 정상화됨. 비교 횟수는 똑같이 2~3번이고, 정리 과정은 데이터 이동이라 비교 횟수에 들어가지 않음.

## 4. [보너스] 재귀적 퀵 정렬 vs 반복적 퀵 정렬

- 두 구현 모두 Median-of-Three 피벗과 같은 `choose_and_partition()`을 사용함
- 반복적 방법은 `(left, right)` 쌍을 배열 스택에 push/pop함 (재귀와 같은 순서가 되도록 오른쪽 구간을 먼저 push)
- n = 10,000, 같은 원본 데이터, 100회 평균. 복사·생성·출력은 측정에서 제외하고 `clock_gettime(CLOCK_MONOTONIC)`으로 정렬 구간만 측정

```
Data Size : 10000
Pivot     : Median-of-Three
(average of 100 runs)

Recursive Quick Sort : 1.0801 ms
Iterative Quick Sort : 1.2129 ms
```

**분석**

- 반복적 방법이 약 12% 느렸음 (0.13 ms 차이).
- 차이가 크지 않은 이유 : 실행시간의 대부분은 partition 안의 비교와 swap인데, 이 부분은 두 방법이 완전히 같음. 재귀 호출과 스택 push/pop은 분할 1번당 2번(왼쪽·오른쪽 구간)만 일어나는데, 분할 1번 안에서는 비교가 구간 길이만큼 일어나므로 전체에서 차지하는 비중이 작음.
- 반복적 방법이 느린 이유 :
  - 정렬할 때마다 스택 배열을 `malloc`/`free`로 할당·해제하는 시간이 측정에 포함됨.
  - 사용자가 만든 스택은 매번 메모리 배열에 값을 쓰고 읽어야 함 (`stack[++top]`, `stack[top--]`). 반면 재귀 호출은 CPU의 호출 스택과 레지스터를 사용하므로 이 과정이 더 가벼움.
  - 최적화 옵션 없이 컴파일하면 이런 배열 접근이 그대로 실행되어 차이가 커짐. 참고로 Linux에서 `-O2`로 컴파일했을 때는 차이가 1% 안팎으로 줄었음.
- 반복적 방법의 장점은 속도가 아니라 안정성임. 재귀는 깊이가 n까지 커지면(예: First 피벗 + 정렬된 데이터) 시스템 스택 오버플로가 날 수 있지만, 반복적 방법은 힙에 만든 스택을 사용하므로 이 위험을 직접 관리할 수 있음.
